# 缺陷定位案例

> **说明**
>
> 本文档是三个真实工作场景的**结构化复盘模板**，对应简历里的三段经历：
> 资金对账、状态流转、多角色权限。
>
> 文中 `【】` 标注的地方需要替换成你自己项目里的真实数据（订单号、金额、时间、缺陷单号）。
> **面试时只讲真实发生过的细节**——结构化的是「怎么想」，不是「发生了什么」。
>
> 写这三个案例的目的：证明「能定位问题」比「会搭框架」更难被替代。

---

## 案例一：账单金额与流水不一致（漏单）

### 1. 现象

对账跑批后，`【某商户】` 当日账单汇总金额比交易流水合计 `【少 ¥1,286.00】`。
账单侧显示 `【37】` 笔，流水侧 `【38】` 笔——**差一笔，而且差的是最大那笔**。

### 2. 影响面

- 商户看到的账是错的，会直接引发投诉和提现争议
- 财务侧按账单记账，金额差会往上放大到结算环节
- 严重程度：**P0**，当天必须定位

### 3. 复现

不是必现，只在特定条件下出现。初步缩小范围：

| 维度 | 观察 |
|---|---|
| 时间 | 集中在 `【23:55 - 00:05】` 跨天时段 |
| 支付方式 | 只有 `【某一种支付渠道】` 出现 |
| 订单特征 | 存在**回调延迟**：支付成功时间与系统入账时间跨了自然日 |

### 4. 定位过程

**第一步：SQL 双向核对，先确认"少了哪一笔"**

```sql
-- 账单侧明细 vs 流水侧明细，找出只在一侧出现的订单
SELECT t.order_no, t.amount, t.pay_time, b.bill_date
FROM trade_flow t
LEFT JOIN bill_detail b ON t.order_no = b.order_no
WHERE t.pay_time >= '【2026-10-01】' AND t.pay_time < '【2026-10-02】'
  AND b.order_no IS NULL;
```

结果锁定 `【1】` 笔：`order_no` 存在，`amount` 正确，但 `bill_detail` 里没有它。

**第二步：追这笔订单的时间线**

```sql
SELECT order_no, status, create_time, pay_time, notify_time, update_time
FROM trade_order WHERE order_no = '【订单号】';
```

关键发现：

- `pay_time` = `【2026-10-01 23:58:12】`（支付渠道返回的支付成功时间）
- `notify_time` = `【2026-10-02 00:00:47】`（我们收到回调的时间）
- 入账时间取的是 `notify_time`

**第三步：确认对账口径**

对账任务按 `pay_time` 划分账期（T 日的账算 T 日），
但入账逻辑用的是 `notify_time`——**两个字段跨天，订单被算进了 T+1 的账**，
而 T 日的账单已经生成完毕。

**第四步：日志交叉验证**

```
grep "【订单号】" app.log
```

日志显示回调在 `00:00:47` 到达，此时 T 日对账批已跑完（`00:00:30` 结束），
订单落到了 T+1 的待对账池。

### 5. 根因

**对账口径字段（`pay_time`）与入账字段（`notify_time`）不一致，且跨天时无补偿机制。**

不是"漏单"，是"错日"。表象是少一笔，本质是账期归属错了。

### 6. 修复与验证

| 动作 | 内容 |
|---|---|
| 修复 | 入账统一取 `pay_time`；跨天回调订单写入"待补账"队列，次日对账前重放 |
| 验证 | 构造 `23:59:59` 支付、`00:00:01` 回调的场景，确认订单归入 T 日 |
| 回归 | 跑 `【近 30 天】` 历史数据比对，确认无新增差异 |

### 7. 沉淀

- **用例**：对账场景必须覆盖「支付时间与回调时间跨天」这一组合
- **检查项**：所有涉及账期的字段，先对齐口径再写断言
- **监控**：每日对账差异笔数与金额双阈值告警

## 案例二：退款成功后订单状态未回滚，出现重复退款

### 1. 现象

商户在后台发起退款，页面提示"退款成功"，但订单列表里状态仍显示「已完成」。
再次点击退款，**系统允许第二次退款**——同一笔订单被退了两次。

### 2. 影响面

- **资损**：直接多退钱给用户
- 商户侧账目与系统账目不一致
- 严重程度：**P0**

### 3. 复现

```
1. 建单并支付 → 订单状态 = 已完成
2. 发起部分退款 → 退款成功
3. 刷新订单列表 → 状态仍为「已完成」
4. 再次发起退款 → 允许提交，再次成功
```

**100% 必现**，只要在第 3 步不等状态刷新。

### 4. 定位过程

**第一步：区分是"状态没更新"还是"状态更新失败"**

查库：

```sql
SELECT order_no, status, refund_status, version, update_time
FROM trade_order WHERE order_no = '【订单号】';
```

结果：`status` 还是「已完成」，但 `refund_status` 已经是「退款成功」——
**同一张表里两个字段互相矛盾**，说明更新只执行了一半。

**第二步：看退款接口的事务边界**

接口逻辑分三步：

1. 调渠道退款接口（外部，成功）
2. 更新 `refund_status`
3. 更新 `order.status`

日志里第 2 步有记录，第 3 步没有——**第 3 步抛异常但被吞了**，
而第 1、2 步已经提交（无事务包裹）。

**第三步：确认幂等**

退款接口的幂等键是 `【order_no + refund_no】`，
但第二次点击生成的是新的 `refund_no`，**所以幂等没有生效**。

### 5. 根因

两个问题叠加：

1. **状态更新与外部调用没有事务边界**，中间失败导致状态不一致
2. **幂等键设计错误**：用"每次新生成"的 `refund_no` 做幂等，等于没有幂等

### 6. 修复与验证

| 动作 | 内容 |
|---|---|
| 修复 | 状态机加"退款中"中间态；外部调用与状态更新改为最终一致 + 补偿任务 |
| 修复 | 幂等键改为 `order_no`，同一订单未完结的退款请求直接拒绝 |
| 验证 | 二次退款返回"退款处理中"；人为中断第 3 步，补偿任务能在 `【5 分钟】` 内收敛 |
| 回归 | 覆盖：全额/部分退款、退款失败重试、退款中再次申请 |

### 7. 沉淀

- **用例**：状态机类功能必须覆盖「每个中间态下的重复操作」
- **经验**：看到"两个字段互相矛盾"，基本可以确定是事务边界或补偿缺失
- **推广**：全量排查其他"外部调用 + 状态更新"的接口，统一加补偿

## 案例三：店员账号能看到全店数据（数据隔离失效）

### 1. 现象

商户老板给店员开了子账号，权限配置为「仅看自己负责的门店」。
但店员登录后，**切换门店后能看到其他门店的营业数据**。

### 2. 影响面

- 数据越权，属于安全问题，不只是功能缺陷
- 商户对平台的信任受损，可能涉及合规
- 严重程度：**P0**（安全类）

### 3. 复现

```
1. 老板账号创建店员 A，绑定门店 1
2. 店员 A 登录，正常只看到门店 1
3. 抓包，把请求里的 storeId 从 1 改成 2，重放
4. 返回门店 2 的完整数据
```

### 4. 定位过程

**第一步：判断是前端过滤还是后端过滤**

直接改请求参数重放 —— 能拿到别的门店数据，
说明**后端没有做数据权限校验，只在前端隐藏了入口**。

**第二步：确认权限校验的落点**

看接口层代码：权限校验只校验了"是否登录"和"是否有该菜单权限"，
**没有校验"该用户是否拥有这个 storeId"**。

**第三步：确认影响范围**

```sql
-- 列出所有只做了菜单级权限、没做数据级权限的接口
SELECT api_path FROM api_permission_config WHERE data_scope = 'none';
```

结果 `【12】` 个接口存在同样问题，涉及订单、账单、员工管理。

### 5. 根因

**权限模型只做到"功能权限"，没做到"数据权限"。**
`storeId` 作为请求参数传入，服务端未校验其归属关系。

### 6. 修复与验证

| 动作 | 内容 |
|---|---|
| 修复 | 统一数据权限拦截器：从 token 取用户，校验 `storeId` 是否在其授权门店列表内 |
| 修复 | `storeId` 不再从请求参数信任，改为服务端根据用户上下文解析 |
| 验证 | 越权请求返回 403；老板/店长/店员三种角色分别回归 |
| 回归 | 对 12 个接口逐个跑越权用例 |

### 7. 沉淀

- **用例**：涉及多角色的功能，必须有一个"越权用例"：改 ID、改角色、重放请求
- **检查清单**：凡是从请求里拿 ID 去查数据的接口，都要问一句"服务端校验归属了吗"
- **左移**：在接口设计评审阶段就要求标注"数据权限落点"

## 三段案例的共同点

| 能力 | 体现 |
|---|---|
| **不止看现象** | 三个都是"表象 A、本质 B"：漏单→错日；状态没变→事务边界；看不清→越权 |
| **用数据说话** | 每一步定位都落到一条 SQL 或一段日志，不靠猜 |
| **定位到根因** | 不是"重试一下好了"，而是说清为什么坏、坏在哪一层 |
| **能沉淀成资产** | 每个案例最后都变成了用例、检查项或监控 |
